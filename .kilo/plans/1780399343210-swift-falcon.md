## Goal
Enhance Nora (local cargo registry at http://127.0.0.1:4000) to include extended metadata for each crate: local clone path, nix build status, pipelight status, vendorsization status, patches, and consumer projects. All fields stored as IPLD-compatible DAG-CBOR in the shared memory server.

## Proposed Changes

### 1. IPLD Storage Schema via Shared Memory Server
Store extended metadata in ipld-car-ipc-shmem-linux server (CAR page format):

```
Storage: Each subsection = one CAR file = one DAG-CBOR object
CID = sha256(DAG-CBOR bytes) ← content-addressed key

Key derivation per subsection:
- local: sha256(DAG-CBOR of local mirror struct)
- nix: sha256(DAG-CBOR of nix build struct)  
- pipelight: sha256(DAG-CBOR of pipelight struct)
- vendor: sha256(DAG-CBOR of vendor struct)
- patches: sha256(DAG-CBOR of patches struct)
- consumers: sha256(DAG-CBOR of consumers struct)
```

CAR format: DAG-CBOR header `{version: 1, roots: [CID]}` + DAG-CBOR block
The shmem server extracts CID from CAR header automatically via `NewMap(car_bytes)`.

### 2. REST API Endpoints
Extend existing `/cargo/api/v1/crates/:name` to include optional query params:
- `GET /cargo/api/v1/crates/:name?extended=true` — include all ipld subsections
- `GET /cargo/api/v1/crates/:name?section=local` — just local clone info (fetch via shmem)
- `GET /cargo/api/v1/crates/:name?section=nix` — just nix build status
- `GET /cargo/api/v1/crates/:name?section=pipelight` — CI pipeline info
- `GET /cargo/api/v1/crates/:name?section=vendor` — vendorsization status
- `GET /cargo/api/v1/crates/:name?section=patches` — patch history
- `GET /cargo/api/v1/crates/:name?section=consumers` — dependent projects

### 4. Integration with cargo-vendormod and IPLD shmem
Add new command to cargo-vendormod that interfaces with shmem server:
```
cargo-vendormod nora-index \
    --workspace-path /mnt/data1/time/2024/05/28/depot/tvix \
    --shmem-socket @ipld_car_shmem
```

This command:
1. Reads the dependency graph from processing output
2. Queries nora HTTP API for each crate's base metadata (name, version, repository)
3. Enriches each crate entry with local paths (git mirrors, flake paths, etc.)
4. Stores DAG-CBOR subsections in shmem server via client protocol
5. Each subsection gets CID-indexed in pages.bin and is content-addressable

### 7. CAR Encoding for DAG-CBOR Subsections
Each subsection must be encoded as a valid CARv1 file:

```text
┌─ CAR Header (DAG-CBOR) ─────────────────────────────────────────────┐
│ {                                                                     │
│   version: 1,              // CARv1                                    │
│   roots: [sha256(DAG-CBOR bytes)],  // CID of the payload              │
│ }                                                                     │
├─ Block (DAG-CBOR) ──────────────────────────────────────────────────┤
│ {                                                                     │
│   type: "local-mirror",     // or "nix-build", etc.                   │
│   url: "https://github.com/serde-rs/serde",                          │
│   mirror_path: "/home/mdupont/git/serde-rs/serde.git",                │
│   ... other fields ...                                                │
│ }                                                                     │
└───────────────────────────────────────────────────────────────────────┘
```

The shmem server's `extract_car_root_cid()` expects CIDv1 with sha256 multihash.

## Questions for Clarification
1. **CID Derivation**: The server extracts CID from CAR header roots (32-byte sha256 of root block). Need to ensure DAG-CBOR encoding includes proper CID in roots field.
2. **Storage Strategy**: Each subsection = one CAR (simpler, matches existing design).
3. **Key Naming**: Content addressed by CID. Need separate index CAR mapping crate names → section CIDs.
4. **Client Library**: Need to create client in cargo-vendormod using postcard + 4-byte length prefix.
