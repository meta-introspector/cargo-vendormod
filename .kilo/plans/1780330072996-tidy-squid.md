# Plan: Vendorize `deep_scanner`, scan `~/dasl`, and extend it toward a pastebin-like webtile/IPFS test-case service

## Goal

Run `cargo-vendormod` on `/home/mdupont/dasl/IMPL/deep_scanner`, then use that scanner on `~/dasl` to:
- enumerate all files as candidate DAG-CBOR encoder/decoder test data
- trace and fuzz the DAG-CBOR implementations based on that data
- serve interesting cases through a Rust interactive webtile server similar to `~/pastebin`
- tag interesting test cases and make them available as IPFS CID/CAR files

## 1) Vendoring `deep_scanner` with `cargo-vendormod`

Subproblem: turn `/home/mdupont/dasl/IMPL/deep_scanner` into a vendored workspace with submodules/mirrors and reproducible flakes.

Proposed steps:
1. Make the vendormod path explicit — replace the broken local-path dep in `deep_scanner/Cargo.toml` with the actual vendormod checkout used in this session, or vendormod-provided path after submodule layout exists.
2. `cargo-vendormod init` from `deep_scanner` → enable git submodules under `submodules/` and mirrors under `mirrors/`.
3. Convert atproto + ipld deps to vendored checkout + `.cargo/config.toml` patch entries.
4. Verify with `cargo check` inside the new vendored/deep-scanner workspace.

Tradeoffs:
- Full vendoring of `atproto-*` and `ipld-*` repos is heavy; for a scanner we can start with vendoring only the DAG-CBOR stack (`serde_ipld_dagcbor`, `ipld-core`, `ipld-car`, `multihash`, `multibase`) and mirrored IPFS repos.
- `deep_scanner/src/main.rs` already imports `workspace::{find_workspace_cargo_files, discover_all_git_repositories}` and `context::AppContext`; vendoring must preserve these paths or add thin re-exports.

## 2) Using the scanner on `~/dasl`

Subproblem: operate `deep_scanner` over `~/dasl` and emit test-case corpora, constants, and traces.

Proposed steps:
1. Build metadata from `deep_scanner/file lists`: `cbor_file_list.txt`, `car_file_list.txt`, `dasl_file_list.txt`, and `pastebin_file_list.txt`.
2. Run `deep_scanner --lang rs,py,toml,json,md,nix,sh` with `--build-corpus` and `--constant-finder` on `~/dasl` sources; write a scanner framing skill that maps each subcommand to the intended DAG-CBOR input class.
3. Export scanner outputs into a new normalized directory:
   - `corpus.txt`
   - `constants.cbor`
   - `CAR` files with embedded findings
   - Python + JSON analysis reports

## 3) DAG-CBOR encode/decode fuzzing and tracing

Subproblem: use scanned files as seed fixtures for encoder/decoder invariants and fuzz tests.

Proposed steps:
1. Add a `fuzz/` harness under `deep_scanner` (or reuse the existing `libipld-fuzz` style) that reads the CAR/constants/corpus outputs as inputs.
2. Inspect target code paths:
   - `serde_ipld_dagcbor::to_vec` + decode
   - `ipld-car` read/write round trips
   - `atproto-dasl` DRISL behavior
3. Generate CBOR corpus entries that exercise tagged/untagged cases, map-key rules, and float restrictions from the DAG-CBOR spec.
4. Add a `deep_scanner` subcommand or sidecar tool called `seed-fuzz` that emits a corpus compatible with `cargo fuzz`, `honggfuzz`, or `libFuzzer` style corpora.

## 4) Interactive webtile server + IPFS tagging

Subproblem: expose interesting cases through an HTTP service with tagging, CID/CAR download, and search.

Proposed steps:
1. Add a new crate or binary inside `deep_scanner` named `tile_server` or `webtile`.
2. Requirements:
   - Serve HTML tiles showing scan findings, constants, and CAR metadata.
   - Allow copy/download of the underlying CBOR/CAR/IPFS CID.
   - Tag cases as `interesting`, `failing`, `roundtrip`, `spec-violation`, `fuzz-seed`.
   - backed by a tiny SQLite or JSON index built from scanner outputs.
3. Wire it into cargo-vendormod’s existing `flake.nix` under `devShells.default` so it can be launched with `nix develop -c tile_server`.
4. Optional: add IPFS publishing from the same tool by calling an embedded local daemon or generating `ipfs add` commands.

## 5) Work breakdown

1. `VENDOR-DEEP-SCANNER` — vendor deps, fix path, initialize vendoring, verify build.
2. `SCAN-DASL` — run `deep_scanner` across `~/dasl`, collect CAR/corpus/constants.
3. `FUZZ-SEEDING` — create seed corpus, trace encode/decode, add fuzz harness stubs.
4. `WEBTILE-SERVER` — add Rust tile server, tags, CID/CAR download, UI.
5. `INTEGRATE-PIPELINE` — connect scanner output to fuzzer inputs to tiles.
